# O1.2a — Atomic Workspace Provisioning (Delivered)

Status: **implemented** (code + migration 0016 + PostgreSQL-backed tests).
Companions: `o1-revised-implementation-plan.md` §2–§3 (governing contracts),
`specialty-pack-architecture.md`, `frictionless-onboarding.md`,
`o1-security-and-data-model.md` §1 (ownership model).

No Docker/Compose/CI/deployment changes. Docker support intact.

## 1. Provisioning API contract

```
POST /api/v1/workspaces
Auth: get_current_user (any active user; verified OR unverified)
Tenant: none required (X-Tenant-less; ignored if supplied)
Headers: Idempotency-Key: <uuid, required>  (missing/malformed -> 422)
Body: {
  clinic_name: str (1..200, stripped, non-empty),
  slug: str (normalized strip().lower(), ^[a-z0-9-]{3,63}$, reserved block,
        unique -> 409 on taken),
  location_name: str (default "Main Clinic"),
  timezone: str (IANA, default "Asia/Kolkata", validated -> 422),
  practitioner_display_name?: str (default = user.display_name),
  specialty_codes: string[] (min 1, registry-validated -> 422)
}
Success: 201 {
  tenant{id,name,slug,status}, location{id,name,timezone},
  membership{id,role:"tenant_admin"},
  practitioner{id,display_name},
  specialties_enabled[...],
  subscription{id,status:"trial",trial_ends_at,plan_code:"trial-14d"}
}
Errors: 401 unauthenticated / 409 slug-taken or idempotency-payload-mismatch /
        422 validation (shape, reserved slug, timezone, specialties, key shape)
```

Hard rules: no `user_id`/`owner` in the body (pydantic ignores extras;
nothing reads them) — the owner is always `ctx.user_id` server-derived.
No verified-email precondition (`require_verified_email` still has zero
production callers; `MeResponse.email_verified` remains a UI hint only).
No payment or communication fields.

Tenant detail extension (additive only): `GET /tenants/{id}` now returns
`subscription{status, trial_ends_at, plan_code} | null` (null for pre-trial
legacy tenants) plus `specialties_enabled[]`. `POST /platform/tenants`
still returns the base `TenantResponse`.

## 2. Transaction boundary and rollback

One transaction (the request's `get_db` scoped transaction). Order:

1. authN; parse + validate `Idempotency-Key` (UUID)
2. normalize + validate body (slug shape/reserved, IANA timezone,
   registry specialties, practitioner name)
3. idempotency claim (`workspace_provisions` insert in a savepoint;
   unique-race -> replay-or-409, same transaction)
4. INSERT tenant (status active) -> `SET app.tenant_id` (server-derived)
5. INSERT location (validated timezone)
6. INSERT membership (seed `tenant_admin`, `is_primary=TRUE`)
7. INSERT tenant_owners (caller only, created_by=caller)
8. practitioner stub: reuse the caller's row by `user_id` if present
   (display_name refreshed), else create linked; per-tenant verification
   row `pending` (approval stays a separate `STAFF_MANAGE` action)
9. INSERT tenant_specialties (one row per code + registry pack_version)
10. INSERT subscriptions (trial row, §4)
11. audit `workspace.provision` + `subscription.trial.start` (refs only)
12. outbox `workspace.provisioned` (refs only; delivery post-P8.1C)
13. mark idempotency `completed` with result refs

Any exception rolls back everything: fault-injection tests prove zero
tenant/location/membership/owner/practitioner/specialty/subscription/
audit/outbox/idempotency rows survive a failure at any stage (8 targets +
slug-conflict mid-path). The idempotency ledger is transactionally
consistent with the provisioned rows by construction (same transaction).

## 3. Idempotency semantics

- Storage: `workspace_provisions(user_id, idempotency_key UNIQUE,
  request_hash CHAR(64), status, tenant_id NULLABLE, result_refs JSONB)`.
- Key scope is the authenticated user: keys never collide across users.
- Same key + same canonical hash -> replay stored 201 (identical body).
- Same key + different hash -> 409.
- Missing/malformed key -> 422.
- Concurrent duplicates: the loser's claim insert blocks on the unique
  index until the winner commits, then replays the winner's 201. Exactly
  one tenant per slug is created. (No process-local state; no TTL sweeper
  needed because `pending` rows cannot survive commit/rollback.)
- The canonical hash covers normalized values (stripped names, lowered
  slug, sorted specialty codes).

## 4. Ownership / membership

`tenant_owners(tenant_id, user_id UNIQUE pair, created_by)` is the
commercial authority; `memberships` (+ seed `tenant_admin`) is the ONLY
access path. Invariants: ownership never grants access (proven: deleting
the membership while keeping the owner row yields 403 on tenant reads);
owner + membership created together; deactivating an owner never deletes
data; one user may own N tenants; cross-tenant access stays blocked
(forged selector -> 403 fail-closed; valid selector + wrong path -> 404
anti-oracle). No `owner_user_id` scalar anywhere.

Last-owner protection for future ownership-management endpoints is
**carryover**: there is no add/transfer/remove owner endpoint in O1.2a,
so the ordered-lock guard has nothing to attach to yet (mirror the
`update_membership` last-admin pattern when the endpoint lands).

## 5. Trial behavior

- Exactly one `subscriptions` row per workspace: plan `trial-14d` (seeded
  by migration 0016, re-seeded in the test harness after TRUNCATE),
  status `trial`, `trial_ends_at = period_end = created + 14 days`
  (server-resolved from `plan.trial_days`; never client input).
- No payment method, no automatic charge, no gateway, no checkout/billing
  UI, no plan tables beyond the single seed row.
- Limits on the seed row (3 locations / 10 practitioners / 25 seats) are
  placeholders, explicitly unenforced in O1 (D6 unresolved).
- Negative tests prove reads behave identically with an expired trial
  fixture (no enforcement interlocks in O1.2a).
- Billing separation holds: no subscription FK in clinic/billing tables,
  no patient/clinical FK in subscription tables (schema test asserts no
  card/payment/charge/gateway columns).

## 6. Specialty persistence decision

- `SPECIALTIES` registry (`app/modules/workspaces/registry.py`):
  `dental v1.0.0` (ready), `ophthalmology v0.1.0` (discovery — accepted
  as an enablement label, builds zero eye workflows).
- `tenant_specialties(tenant_id, specialty_code, pack_version)` is the
  initial source of truth. Locations inherit the tenant set by
  convention. **No `location_specialties` table in O1.2a**: the both-level
  model is proposed-but-unresolved (needs real operational requirement);
  introducing it now would be speculative schema.
- No silent default: `specialty_codes` is required (min 1); the dental
  default is proposed, not approved. Empty/unknown codes -> 422.
- Specialty checks never touch identity, authorization, RLS, billing, or
  tenant isolation (existing suites re-verified).

## 7. Timezone

`is_valid_iana_timezone` (shared with the notification eligibility gate,
`ZoneInfo` resolution) validates `timezone` on the provisioning path and
rejects unknown identifiers (422, no silent fallback). Timestamps persist
in UTC (`timestamptz`); the location timezone is stored for local
scheduling/display. The pre-existing `create_location` default
(`Asia/Kolkata`) is unchanged for the operator path.

## 8. Security / RLS review

- Tenant/user ids server-derived; slug server-normalized; plan/status/
  bounds server-resolved. Caller-supplied ids ignored (tested).
- RLS `FORCE` on `tenant_owners`, `subscriptions`, `tenant_specialties`
  (tenant-isolated) and `workspace_provisions` (user-isolated,
  `user_id = ACTOR`, mirroring the memberships bootstrap exception).
  `subscription_plans` is a non-RLS readable catalog (roles precedent).
- Cross-tenant SELECT/INSERT/UPDATE/DELETE proven blocked at the SQL
  layer; existing RLS/isolation/portal suites re-verified green.
- Audit/outbox payloads are references only (`*_id`); the port-safety
  blacklist test passes; no tokens/passwords/contacts in logs
  (DEV-ONLY verify link logging untouched).
- No auth/RLS/rate-limit/audit behavior weakened.
