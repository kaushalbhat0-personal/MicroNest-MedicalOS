# O1.3R — Subscription & Specialty Read-only Visibility (Delivered)

Status: **implemented** (migration 0017 + additive API/schemas + PostgreSQL-backed tests).
Companions: `o1.2a-workspace-provisioning.md` (provisioning contract — unchanged),
`subscription-domain-discovery.md` (lifecycle proposal — still deferred),
`o1-revised-implementation-plan.md` §9 (O1.3R is step 4 of the approved sequence),
`specialty-pack-architecture.md` (readiness source of truth).

No Docker/Compose/CI/deployment-architecture changes. Docker support intact.

## 1. What this slice does (and does not do)

Read-only visibility over the subscription and specialty records created by
O1.2a. Two additive read contracts (tenant-facing, platform-facing), plan
catalog integrity hardening, specialty readiness metadata, and
schema/contract proof that the commercial and clinic-billing domains stay
separate.

Explicitly NOT implemented (no code paths exist for any of these):
trial-expiry enforcement, suspension/reactivation, grace/dunning/cancellation,
payment collection, Razorpay or any gateway, plan upgrades/downgrades,
proration/refunds, entitlement enforcement, location/practitioner/seat limit
enforcement, owner-management endpoints, branding/white-label, licensing
enforcement, email/WhatsApp providers, patient onboarding changes,
ophthalmology workflows, marketing site, EXE/APK, general analytics, full
platform console, Docker changes, provider/portal improvements.

## 2. Tenant-facing read contract

`GET /api/v1/tenants/{id}` (existing route, `TENANT_READ` + `match_tenant`,
extended additively — no duplicate API). All fields are server-resolved
snapshots; no mutable ORM objects leave the API (explicit Pydantic schemas).

```jsonc
{
  "id": "uuid", "name": "…", "slug": "…", "status": "active",
  "subscription": {
    "status": "trial",                    // persisted status
    "trial_ends_at": "…",                 // persisted (period_end mirrors it)
    "plan_code": "trial-14d",             // stable identifier
    "plan_name": "Trial (14-day)",        // display name from the catalog row
    "trial_starts_at": "…",               // persisted period_start
    "is_in_trial": true,                  // derived: status=="trial" AND now<=trial_ends_at
    "limits": {
      "max_locations": 3, "max_practitioners": 10, "max_staff_seats": 25,
      "enforced": false                   // INFORMATIONAL ONLY, unenforced
    }
  },
  "specialties_enabled": ["dental"],      // legacy code list (kept for compat)
  "specialties": [                        // NEW: code + persisted pack version + readiness
    {"code": "dental", "pack_version": "1.0.0", "label": "specialty.dental",
     "maturity": "ready", "ready_for_use": true}
  ]
}
```

- `subscription` is `null` for pre-trial legacy tenants (unchanged).
- `limits` are the seeded placeholders (3/10/25); nothing reads them to
  gate behavior (grep-verified: only the trial-creation path reads
  `trial_days`; no `max_*` consumer exists).
- `is_in_trial` is derived per request from persisted status + dates and is
  never written back.
- Authorization: tenant context + membership resolved server-side
  (`get_ctx`); caller-supplied tenant ids are selectors only; 403 for
  foreign selectors, 404 anti-oracle for foreign path ids (both preserved
  and tested). Every role holding `tenant.read` sees the same permitted
  summary; roles without it get 403. No commercial cost, provider,
  credential, payment, or platform metadata is exposed.
- Frontend: the tenant `/admin` page renders a read-only Subscription card
  (plan, status + in-trial badges, trial window, informational limits,
  specialty readiness) from this contract via the existing `useTenantApi`
  pattern; statuses map through `presentStatus` (`packages/ui/status.ts`).

## 3. Platform-facing read contract

 gated exclusively by the existing `is_platform_admin` user flag
(`get_platform_admin` — never tenant membership, headers, or body).

- `GET /api/v1/platform/tenants?limit=20&offset=0&status=active`
  → `{items: [PlatformTenantItem], total, limit, offset}`.
  Bounded pagination (`limit` 1..100, `offset` >= 0); optional `status`
  filter (`active|suspended|deactivated`, else 422). Unknown tenants are
  404. The item shape is the tenant identity + timestamps + the same
  `subscription` summary and `specialties` detail as §2 — and nothing else.
- `GET /api/v1/platform/tenants/{tenant_id}` → one `PlatformTenantItem`.
- Deliberately absent: clinical records, patient data, staff personal data
  (no owner/user rows — only refs stay server-side), credentials, secrets,
  tokens; location/membership **counts** (deferred: `locations` and
  `memberships` are tenant-pinned RLS tables and counts would need their
  own RLS review — see §9 carryover); any write method (POST/PATCH/DELETE
  on the read views are 404/405, tested).
- Efficiency: one page query + one `IN` query each for subscriptions,
  plans, and specialty rows (no N+1, tested by shape, not timing).
  `total` comes from a single `COUNT(*)`.

## 4. Authorization and RLS review

- Tenant path unchanged: `get_ctx` → `require(tenant.read)` →
  `match_tenant` → RLS tenant pinning. Ownership still grants nothing
  (existing tests re-verified green).
- Platform path: `get_current_user` (401 when anonymous, sets
  `app.user_id`) → `get_platform_admin` (403 unless
  `is_platform_admin`). Ordinary tenant admins get 403 on both platform
  routes; anonymous callers get 401 (tested).
- Migration 0017 adds two **SELECT-only** RLS policies
  (`subscriptions_platform_read`, `tenant_specialties_platform_read`)
  whose `USING` clause is `EXISTS (… users … is_platform_admin AND
  is_active)`. They are purely additive: the existing tenant-pinned
  `FOR ALL` policies are untouched, permissive policies OR for reads, and
  the new policies have no `WITH CHECK`, so the platform path cannot write
  subscription/specialty rows even if an endpoint bug tried (read-only at
  the database layer). Clinical, billing, portal, membership, and location
  tables have no platform policy — the platform still has no clinical path.
- `subscription_plans` stays a non-RLS readable catalog (as in O1.2a).

## 5. Plan catalog uniqueness and seed behavior

- `UNIQUE(code)` on `subscription_plans` (from 0016) remains the primary
  duplicate guard (constraint-presence asserted in tests; a duplicate
  insert raises `IntegrityError`).
- Migration 0017 re-seeds `trial-14d` with `ON CONFLICT (code) DO NOTHING`,
  so duplicate migration execution or repeated seed execution cannot create
  a second trial plan (tested: seed run twice → exactly one row; fresh
  `alembic upgrade head` + full `downgrade base` + `upgrade head` green).
- Lookup is deterministic: `get_plan_by_code` orders by `created_at` and
  returns the single row; `get_trial_plan` additionally fails closed when
  the plan is missing or inactive. `create_trial_subscription` (the only
  writer) uses `get_trial_plan`.
- Seed values are unchanged: `trial-14d` / "Trial (14-day)" /
  3 locations / 10 practitioners / 25 seats / 14 days / active.
  The limits are placeholders and unenforced (see §7).

## 6. Trial visibility semantics and explicit non-enforcement

- Every provisioned workspace still gets exactly one `subscriptions` row
  (`trial`, `trial_ends_at = period_end = period_start + 14d`, server
  clock, no client input) — re-verified.
- `is_in_trial` is a read-time derivation only. Proof of non-enforcement:
  fixtures with an expired `trial_ends_at` and with `status='suspended'`
  read identically (tenant detail 200, locations 200, `is_in_trial=false`)
  — commercial state changes nothing about clinical read availability in
  this phase.

## 7. Specialty readiness representation

Source of truth: `app/modules/workspaces/registry.py`
(`dental v1.0.0` ready, `ophthalmology v0.1.0` discovery) — unchanged by
this slice; provisioning behavior is byte-for-byte the O1.2a contract.

- The read model exposes, per persisted enablement row: `code`,
  persisted `pack_version`, registry `label`, `maturity`
  (`ready|discovery`, `unknown` for codes with no registry entry), and
  `ready_for_use` (`maturity == "ready"`). Readiness is display-only: it
  never feeds authorization, RLS, tenant identity, or subscription logic
  (behavioral test: an ophthalmology-only workspace authorizes identically
  to a dental one).
- Ophthalmology renders as **"Discovery only"** (warning badge) — never as
  an available clinical workflow. No eye schema, forms, workflows,
  catalogs, or authorization rules were added. The response carries
  readiness metadata only (exact key set asserted).
- Unknown codes fail safe (`maturity: "unknown"`, not operational).
- Audit note: discovery-only specialties remain enableable as labels (the
  accepted O1.2a provisioning semantic). That is now *visibly*
  discovery-only in every read surface, so no silent-misrepresentation
  fix was needed. Smallest corrective follow-up (O2, proposed): gate
  ophthalmology enablement behind doctor sign-off or render an explicit
  "not operational" banner in the provisioning UI. No provisioning change
  was made here.

## 8. Billing separation evidence

- Schema test (information_schema): no FK from `subscriptions` /
  `subscription_plans` to any clinic table (invoices, payments,
  allocations, receipts, refunds, credit notes, estimates, patients,
  encounters, portal links); no FK from any clinic/billing table to any
  subscription table. No `patient_subscriptions`, `subscription_invoices`,
  or `subscription_payments` tables exist; the plan catalog holds exactly
  `trial-14d`.
- Behavioral test: provisioning creates zero rows in all seven clinic
  billing tables for the new tenant.
- Contract test: tenant detail, platform list, and platform detail
  responses contain no invoice/payment/allocation/receipt/refund/credit/
  card/charge/gateway keys or values.
- Independence test: a legacy subscription-less tenant enrolls a portal
  link normally — portal access is not gated on any subscription, and no
  patient subscription SKU exists anywhere.
- Existing clinic billing behavior is unchanged (billing suites re-run
  green; the subscription module still imports no billing code and billing
  imports no subscription code).

## 9. Remaining risks and follow-up work (carryover, not blocking)

1. Location/membership counts for the platform list need their own RLS
   review (new SELECT policies or an audited reporting path) — O1.4R.
2. Ophthalmology enablement gating behind sign-off (see §7).
3. Trial-expiry/suspension semantics, grace, dunning, plan changes,
   metering, subscription billing tables — O2 (D6/D9/D10 open).
4. Last-owner guard + owner add/transfer endpoints — O2.
5. Full platform console (search, detail actions, audit of platform reads)
   — O1.4R. Platform reads are currently unaudited (tenant audit reads
   are; platform list/detail are not — acceptable for metadata reads,
   revisit in O1.4R).
6. Frontend: the subscription card lives on the tenant `/admin` page; a
   platform console screen is intentionally not built (O1.4R owns it).
