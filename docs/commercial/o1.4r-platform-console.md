# O1.4R — Read-only Platform Admin Console (Delivered)

Status: **implemented** (backend audit on O1.3R platform APIs + Next.js console
pages + PostgreSQL-backed tests). No migration. No RLS change.
Companions: `o1.3r-subscription-specialty-visibility.md` (API contracts —
unchanged), `o1.2a-workspace-provisioning.md`, `o1-security-and-data-model.md`,
`docs/security/*`, `docs/product/multi-platform-product-architecture.md`,
`DESIGN.md`.

No Docker/Compose/CI/deployment-architecture changes. Docker support intact.

## 1. What this slice does (and does not do)

A read-only Platform Admin Console for the O1.3R platform APIs, with audited
reads. Two console pages (tenant directory + tenant detail), one shared
platform fetch hook, one identity gate, and per-tenant audit events for
every successful platform read.

Explicitly NOT implemented: counts (location/membership — deferred, §5),
owner identity or owner references (deferred, §4), tenant impersonation,
support bypass, any write operation, subscription enforcement, payment
gateway/checkout/billing/plan changes/cancellation, provisioning contract
changes, ophthalmology workflows or readiness promotion, role-aware
navigation (carryover, §9), marketing site, EXE/APK, general analytics,
Docker changes.

## 2. Tenant directory (`/platform/tenants`)

- Paginated tenant list via `GET /api/v1/platform/tenants` (server-bounded
  `limit` 1..100, `offset`, page size 20, "Load more" accumulation using the
  existing `Pagination` component).
- Server-side tenant-status filter (`status=active|suspended|deactivated`,
  native `Select`); changing it resets the list. No client-side search box:
  the API supports no search, and page-scoped filtering would mislead.
- Table columns keep the two domains visibly separate: Workspace (name +
  slug) | Tenant status | Plan | Subscription status | Trial ends |
  Specialties. Row names link to the detail page.
- States: initial loading skeleton, sign-in prompt (anonymous), forbidden
  (non-admin, incl. API 403 race), error + Retry, empty (no workspaces /
  no matches for filter).
- Footer note states the deliberate omissions: owner information and
  location/membership counts are not exposed in this phase.

## 3. Tenant detail (`/platform/tenants/{id}`)

- Identity card: name/slug, tenant status badge, created/updated
  timestamps, with helper text separating tenant status (account domain)
  from subscription status (commercial domain).
- Subscription card: plan name + code, subscription-status + in-trial
  badges, trial window, plan limits labelled **informational only, not
  enforced**, and a note that each view is recorded in the workspace's
  audit trail.
- Specialties card: code + persisted pack version + readiness badge.
  Ophthalmology renders **Discovery only** (warning); readiness is display
  metadata, never a workflow affordance. No clinical, billing, portal, or
  personal data appears anywhere (key-set asserted in tests).
- Unknown ids render "Workspace not found" (API 404); anonymous/forbidden
  handling matches the directory page.

## 4. Owner reference — deferred with documented gap

Review outcome: the only owner record is `tenant_owners(user_id)`; any
human-readable owner reference requires joining `users` (email,
display_name = staff PII). The O1.3R API exposes no owner field, so the
console shows none — the detail page states this explicitly rather than
implying data.

Options considered and rejected for this slice:
- Owner identity (email/name): rejected — staff personal data, no privacy
  sign-off, no legitimate read-only-phase need.
- Owner *count*: rejected for now — `tenant_owners` is a tenant-pinned RLS
  table; even a bare count needs a new platform SELECT policy (same class
  of change as §5). Value does not justify expanding the RLS surface.

Follow-up (needs privacy sign-off): `owner_count` via a SELECT-only policy
on `tenant_owners` (count only, no ids), or an `owner_refs` projection.
Nothing to migrate or RLS-review until then.

## 5. Location and membership counts — deferred with documented decision

Review outcome: `locations` and `memberships` are tenant-pinned RLS tables;
`memberships` rows link user ids (identity-adjacent). Exposing counts to
the platform path would require new platform SELECT policies on those
tables — a wider RLS exception than the O1.3R commercial-metadata policies
(`subscriptions`, `tenant_specialties`), for operator-curiosity value only.
Per the authorisation brief ("do not expose counts unless tenant scoping
and platform access are explicitly justified and tested"), they are
deferred: the API returns no counts, the UI states the omission, and no
migration or policy was added. Follow-up: dedicated RLS review + tests if
operators demonstrate need (O2 console hardening).

## 6. Authorization design (unchanged, reused)

- Server is authoritative: `get_current_user` (401) →
  `get_platform_admin` (existing `is_platform_admin` flag, 403 otherwise).
  No client-supplied role, header, tenant membership, or body value is
  trusted. Deny by default at every layer.
- The frontend gate (`usePlatformMe`, no `X-Tenant` header) is UX only:
  anonymous users see a sign-in prompt, non-admins see "Platform access
  required", and API 401/403 responses render the same states (race-safe).
- Tenant isolation preserved: platform admins hold no membership, so all
  tenant-scoped routes (patients, tenant detail, …) still return 403 for
  them — asserted in tests alongside console access.

## 7. Audit design (new in O1.4R)

- `platform.tenant.read` (detail) and `platform.tenant.list` (one per
  returned item) events are appended into the **viewed tenant's own
  hash-chain** (`audit_events`, refs only: actor user id, resource
  tenant/id, request id, result `ok`). Residents of a workspace can see
  platform access in their own trail; no cross-tenant audit reads are
  created (platform has no audit-read API).
- Mechanism: existing `audit_service.append` + per-tenant
  `SET app.tenant_id` (service-verified target, same pattern as
  `POST /platform/tenants`). **No shared-infra change**: no new tables,
  columns, actions plumbing, or RLS policies — which is why no migration
  was needed.
- Correctness findings (both covered by tests):
  - Flush-while-pinned: ORM autoflush defers an `append`'s INSERT until
    the next query, at which point a list loop may already have moved
    `app.tenant_id` to the next tenant (row then fails `WITH CHECK`).
    The helper therefore `db.flush()`es immediately after each append
    while the correct tenant context is active.
  - Failures mint nothing: 401/403/404/422 paths return before any
    append (unknown ids have no chain to record in). Chain verification
    (`verify_chain`) passes for audited days.
- Cost: list audits are bounded by the page limit (≤100 inserts,
  operator-frequency endpoint). Rejected alternative: a single list-level
  event has no tenant chain to live in without inventing a platform audit
  sink — a larger change than the problem warrants.

## 9. Remaining risks and carryovers

1. Role-aware navigation: the console is reachable at `/platform/tenants`
   (documented); the static `NAV` is unchanged to avoid touching shared
   chrome. Follow-up: conditional platform link after `me` resolves.
2. List-audit write amplification (≤100/invocation) — accepted, monitor if
   operator usage grows; alternatives (platform audit sink, sampled
   auditing) are larger changes.
3. Owner count / owner refs — needs privacy sign-off (§4).
4. Location/membership counts — needs dedicated RLS review (§5).
5. O2 enforcement, checkout, plan changes, ophthalmology gating, and the
   full O1.5R E2E remain untouched.
